# GatherVis 项目计划书（暂定名）

**开源叠前地震数据交互式查看器 —— 面向 Python 生态与 GPU 服务器环境**

版本：v0.1（立项讨论稿） · 日期：2026-08-10

---

## 1. 一句话定位

做叠前数据领域的 cigvis：让科研人员在 GPU 服务器上，用几行 Python 代码 + 一个浏览器，交互式地查看、QC 正演/实测的叠前地震道集数据。

## 2. 背景与动机

当前地球物理科研的重心已经全面转向 Python 生态，且工作环境普遍是无显示器的 GPU 服务器（正演、FWI、叠前 AI 任务都在上面跑）。叠后三维数据的查看已经被 cigvis 很好地解决，其成功证明了"几行代码可用 + 贴合科研工作流"这条路线的价值。但叠前数据（炮集、CMP 道集、共偏移距道集）至今没有对应的系统性开源工具：大家要么用 matplotlib 一张张 imshow，要么把数据拖回本地用商业软件（Geoeast、Omega、INTViewer 等）查看。商业软件功能完备但闭源、昂贵、且不在服务器 Python 工作流里。本项目的目标就是把商业软件中"叠前数据浏览与 QC"这一子集，以开源、高性能、服务器友好的方式在 Python 生态中复刻出来。

## 3. 设计原则

1. **性能优先**。懒加载、按需读取、GPU 加速处理；打开 100 GB 的正演炮集应当秒开，换炮应当无感。
2. **服务器优先（web-first）**。默认使用场景是 SSH 连接 GPU 服务器，浏览器 + 端口转发即可交互；桌面窗口是可选项而非前提。
3. **几行代码可用**。API 手感对齐 cigvis：`import gathervis as gv; gv.show(data)` 即可看图，复杂配置全部可选。
4. **两种输入模式并存**。"无观测系统的快速查看"与"带观测系统的系统浏览"是两个平级的入口，前者绝不因后者的存在而变复杂。
5. **渐进式功能**。查看器不是处理系统，不做全功能商业软件复刻；每一期只交付一小组打磨完整的功能。

## 4. 核心概念与数据模型

### 4.1 观测系统的统一定义

观测系统 = 每一炮与每一道的空间位置关系，炮点与检波点位置均由 XYZ 三坐标确定。本项目不在数据模型层面区分"二维地震"与"三维地震"——两者的区别只在接收排列方式上：

- 放一炮时只有一条测线在接收 → 该炮的共炮点道集是二维数组 `(nrec, nt)`；
- 放一炮时整个面元排列都在接收 → 该炮的共炮点道集是三维数组（如 `(nrec_y, nrec_x, nt)`）。

因此统一的数据表示是：**炮点坐标数组 `src_xyz (ns, 3)` + 检波点坐标数组 + 数据体**。MVP 阶段先支持规则观测系统（所有炮共享同一套检波点排列，或检波点坐标可表示为 `(ns, nr, 3)` 的规则数组）；不规则观测系统（每炮检波器数量/位置不同）通过道索引表（trace table）在后续里程碑支持。

### 4.2 两种输入模式

**模式 A：无观测系统的快速查看。** 输入就是一个 numpy 数组 / memmap / 二进制文件 + shape：

- 二维数组 `(ntrace, nt)`：单个共炮点道集或 CMP 道集，一张 image 图直接画出，追求"比 plt.imshow 更快更好用"；
- 三维数组：可能是"三维地震的一个共炮点道集"（一个体），也可能是"二维地震的整条测线 `(nshot, nrec, nt)`"。**已定案的默认行为**：不加任何参数时，默认解释为 `(炮, 道, 时间)` 并进入逐炮翻页浏览（贴合叠前使用直觉）；用户可通过 `view='slices'` 切换为 cigvis 式三方向切片浏览。语义与视图解耦：`axes` 声明数组各维含义（如 `axes=('recy','recx','time')` 显式声明为三维炮集体，此时自动采用切片视图），`view` 声明浏览方式，两者均可独立覆盖默认值。

**模式 B：带观测系统的系统浏览。** 输入 = 数据 + 观测系统（炮点坐标、检波点坐标）。界面上呈现观测系统平面图（炮点、检波点散点图），点击某个炮点（或在侧边列表中选择）即联动显示该炮的共炮点道集：二维地震情形显示二维道集图，三维地震情形显示可切片的三维小体。

### 4.3 域（domain）的概念（为 M3 预留）

同一份叠前数据存在多种观察视角：共炮点域、共检波点域、CMP 域、共偏移距域。抽道集的本质是"按某个 key 对道重新分组排序"。数据模型从一开始就以"道 + 道属性（炮号、检波点号、坐标、偏移距、CMP 号）"为底层抽象，规则数据只是这个抽象的一种高效特例。这保证 M3 的"自由抽道集"不需要推翻 M1 的架构。

## 5. 需求清单与里程碑

### M0 —— 项目骨架（基础设施）

数据对象（`GatherDataset` / `Geometry`）的定义与单元测试；NumPy/CuPy 双后端的计算抽象；合成示例数据生成器（简单层状模型正演或解析走时 + Ricker 子波，用于所有 demo 与测试）；仓库、CI、文档站骨架。

### M1 —— 第一步：共炮点道集可视化（本期交付核心）

模式 A（无观测系统）：

1. `gv.show(array_2d)`：单道集图像视图，默认 percentile 截断 + 地震色标，浏览器中缩放/平移流畅；
2. `gv.show(array_3d, axes=...)`：体视图，三个方向的切片轴可鼠标拖动（对齐 cigvis 交互习惯）；同一入口支持 `(nshot, nrec, nt)` 的逐炮翻页浏览模式（键盘 ←/→ 或滑块换炮）。

模式 B（带观测系统）：

3. 观测系统导入：接受 numpy 数组（`src_xyz`、`rec_xyz`）或简单文本/npz 文件；
4. 观测系统平面图：炮点/检波点散点显示，可缩放平移；
5. 联动浏览：点击平面图中的炮点或在列表中选择炮号 → 右侧显示对应共炮点道集（2D 情形二维图 / 3D 情形三向切片体）；当前炮在平面图中高亮。

通用：

6. 服务器友好交付：`gv.show(..., port=8080)` 启动服务，SSH 端口转发后本地浏览器访问；
7. 懒加载：数据以 memmap/zarr 方式按需读取，打开大文件不整体载入内存。

### M2 —— 第二步：可视化细节打磨

色标切换（内置地震常用色标，兼容 matplotlib colormap 名）；上下限调整（手动 clim + percentile 快捷档）；增益（dB 步进）；AGC 开关（窗长可调）；道均衡（trace balance/normalization，按道最大值或 RMS）；image 与 wiggle（波形加变面积）两种显示方式切换；多面板对比与视图同步（对齐 cigvis 的 share camera 体验）；截图/导出 PNG。其中 AGC、滤波、道均衡等即时处理在数据位于 GPU 时用 CuPy 执行，形成相对商业软件的差异化优势（数据本来就在 GPU 服务器上）。

### M3 —— 第三步：自由抽道集

道属性索引层（每道的炮号、检波点号、坐标、偏移距）；CMP 坐标计算与面元划分（binning）；按任意 key 抽道集：共炮点 / 共检波点 / CMP / 共偏移距；道集内按 offset 排序显示；覆盖次数（fold）平面图；SEG-Y 导入（segyio 扫描道头建索引，索引持久化，之后抽道集为查表 + 按需读盘）。

### M4 —— 第四步：切片与拾取

共偏移距体的三向切片、时间切片；手动同相轴拾取（鼠标点选、拖动、导出坐标文件）；初至自动拾取的插件钩子（STA/LTA 等经典算法内置一个参考实现，深度学习拾取留接口）；NMO 动校正实时预览（速度参数滑块，CuPy 实现，为远期速度分析铺路）。

### 非目标（明确不做）

完整处理流程系统（去噪、偏移等作业式处理）；解释系统（层位库、断层库、井震标定）；多用户协作与权限；SEG-Y 写出与格式转换工具链（交给 segyio/MDIO）。

## 6. 技术选型

### 6.1 语言问题：为什么主体是 Python，以及"快"从哪里来

这个项目的性能瓶颈按重要性排序是：**磁盘 IO（读道集）> 数据传输（服务器→浏览器）> 渲染 > 数值计算 >> 解释器开销**。逐项对策：

- **IO**：memmap / zarr 分块 + 只读需要的道集，这是架构问题，与语言无关；
- **传输**：float32 在服务器端完成 colormap 前的归一化，量化为 uint8（可选 WebP/PNG 压缩）再传输，数据量降到 1/4 以下；大剖面用降采样金字塔（LOD），放大到哪里再取哪一级细节；
- **渲染**：交给浏览器 GPU（WebGL）或服务器端离屏渲染，都不走 Python 循环；
- **计算**：AGC/滤波/NMO 全部 NumPy 向量化，GPU 上用 CuPy（API 同构，双后端一套代码）；个别无法向量化的索引/binning 热点用 Numba JIT。

在这个架构下，Python 只做编排，本身不在热路径上。关于 Go：Go 无法作为 Python 的进程内扩展（只能走子进程/RPC，交互延迟反而更高），且科学计算生态薄弱，不适合本项目。如果未来确实出现纯 Python/Numba 压不住的热点（比如亿级道头的扫描索引），正确的升级路径是 **Rust（PyO3/maturin）或 C++（pybind11）扩展模块**——这也是当前 Python 生态处理性能热点的主流做法（polars、tokenizers 均如此）。结论：**Python + NumPy/CuPy/Numba 起步，Rust 扩展作为预留的后手，不在 MVP 引入。**

### 6.2 前端/渲染方案

原则：**数据服务与前端解耦**。核心层暴露"给我第 i 炮道集 / 给我某切片"的接口，前端只是消费者，将来可替换升级。

| 方案 | 优点 | 缺点 | 定位 |
|---|---|---|---|
| Panel/Bokeh 或 Plotly Dash | 开发极快，纯 Python，交互组件齐全 | 大数据/高频交互性能有上限 | M1 快速落地首选 |
| viser（cigvis 同款） | 3D 场景现成，SSH 友好，与 cigvis 体验一致 | 偏 3D 场景，2D 道集浏览组件需自己搭 | 三向切片体视图可直接借鉴/复用 |
| FastAPI + WebSocket + 自研 WebGL 前端 | 性能上限最高，交互完全可控 | 开发量大，需要前端技能 | M2/M3 之后的演进方向 |
| vispy 桌面窗口 | 本地体验好，cigvis 有成熟代码可参考 | X forwarding 下不可用，违背服务器优先 | 可选后端，低优先级 |

建议路线：M1 用 Panel（Bokeh 后端）做 2D 道集浏览器与观测系统平面图，三向切片借鉴 cigvis 的 viser/sliceviewer 实现；同时把核心层接口设计成与前端无关，为 FastAPI + WebGL 的演进留门。

### 6.3 数据 IO 与格式

原生输入：`np.ndarray`、`np.memmap`、`.npy`、原始二进制 + shape/dtype 参数（覆盖正演场景 90% 的需求）。大数据：zarr（分块、压缩、云友好）。实测数据：segyio（M3 引入，扫道头建索引）；MDIO 作为可选后端评估。观测系统：numpy 数组直接传入，或 `.npz`/简单文本格式。

### 6.4 分层架构

```
gathervis/
├── core/        # GatherDataset, Geometry, 道属性索引, 语义轴
├── io/          # numpy/memmap/zarr 读取器; (M3) segy 索引器
├── process/     # gain, agc, balance, bandpass, nmo —— numpy/cupy 双后端
├── server/      # 数据服务: 道集/切片/平面图的取数与量化传输
├── viz/         # Panel 前端组件; 切片体视图; (远期) webgl 前端
└── api.py       # gv.show(), gv.from_array(), gv.from_segy() 等顶层入口
```

## 7. API 草案

```python
import gathervis as gv

# ---- 模式 A: 无观测系统快速查看 ----
gv.show(gather_2d)                                  # (ntrace, nt) 单道集
gv.show(vol)                                         # 三维数组: 默认按 (炮, 道, 时间) 逐炮浏览
gv.show(vol, view='slices')                          # 同一数组, 切换为三向切片体视图
gv.show(vol, axes=('recy', 'recx', 'time'))          # 显式声明为三维炮集体 -> 自动切片视图
gv.show('shots.bin', shape=(201, 301, 1500),
        dtype='float32', dt=0.002,
        axes=('shot', 'rec', 'time'))                # 文件 + memmap 懒加载

# ---- 模式 B: 带观测系统 ----
ds = gv.from_array(data,                             # (ns, nr, nt) 或 (ns, nry, nrx, nt)
                   src=src_xyz,                      # (ns, 3)
                   rec=rec_xyz,                      # (nr, 3) 或 (ns, nr, 3)
                   dt=0.002)
gv.show(ds, port=8080)   # 左侧观测系统平面图, 点炮点 -> 右侧共炮点道集

# ---- M2/M3 预览 ----
gv.show(ds, agc=0.5, cmap='gray', clim='p98', wiggle=False)
gv.show(ds.cmp(bin_size=25), domain='cmp')           # 抽 CMP 道集
```

## 8. 工程规范

MIT 许可证；仓库含 `examples/` 合成数据脚本（保证任何人 clone 后 30 秒内看到第一张图）；pytest 单元测试覆盖 core/process；GitHub Actions CI（含无 GPU 环境的 CuPy 跳过逻辑）；文档用 sphinx + gallery（对齐 cigvis 的文档形态，降低用户迁移成本）；中英双语 README。命名候选：gathervis / psvis / previs（待定，需检查 PyPI 占用）。

## 9. 风险与开放问题

1. **三维数组语义歧义（已定案）**：默认解释为 `(炮, 道, 时间)` 逐炮浏览；`view='slices'` 切换为体切片浏览；`axes` 参数可显式覆盖语义声明。M1 按此实现。
2. **不规则观测系统**：MVP 只支持规则排列；不规则情形的道索引表设计（内存占用、查询效率）是 M3 的主要技术风险。
3. **前端性能上限**：Panel/Bokeh 在万道级道集 + 高频交互下可能吃紧，需在 M1 结束时做一次性能评测，决定 M2 是否提前启动 WebGL 前端。
4. **与 cigvis 的关系**：保持独立项目，但交互习惯、文档形态、API 手感主动对齐 cigvis，切片组件优先考虑复用其代码（MIT 许可证兼容），远期不排除生态整合。
5. **超大数据（>100 GB 正演输出）**：zarr 分块 + LOD 金字塔的生成时机（导入时预生成 vs 首次访问时缓存）待 M2 评估。
